# Решения и допущения

Здесь собраны вопросы, на которые ТЗ не даёт однозначного ответа, и решения, которые я по ним принял.

## Роли и пользователи
1. **Роль хранится в таблице `profiles`**, а не в метаданных пользователя: метаданные регистрации может задать сам пользователь. Профиль создаётся триггером при создании пользователя и **всегда получает роль «Исполнитель»**. Постановщика назначают вручную SQL-запросом, через API роль изменить нельзя.
2. **Один пользователь — одна роль.** Постановщик не может быть исполнителем задачи: база это проверяет.
3. **Имена и роли всех пользователей видны всем вошедшим.** Без этого постановщик не выберет исполнителя, а исполнитель не увидит в истории, кто вернул ему задачу. Никаких других данных в профиле нет.

## Задачи
4. **У каждой задачи обязательно есть исполнитель.** ТЗ описывает переходы «назначенного исполнителя», а у задачи без исполнителя никто не смог бы двинуть её дальше «Новой».
5. **Постановщик может редактировать задачу в любом статусе**, включая смену исполнителя. После смены исполнителя дальше задачу ведёт новый исполнитель, а старый перестаёт её видеть. Статус и автор при этом не меняются.
6. **Любой постановщик может принимать и возвращать любые задачи**, а не только свои. В ТЗ сказано просто «постановщик», и постановщиков может быть несколько.
7. **Статус меняется только через функцию `change_task_status`**, прямое изменение колонки запрещено. Так проверка переходов и запись истории всегда происходят вместе, в одной транзакции.
8. **Комментарий можно добавить к любому переходу**, но обязателен он только при возврате на доработку. В интерфейсе поле комментария показывается только для доработки, чтобы не усложнять экран.

## Удаление
9. **При удалении объекта удаляются его задачи, а при удалении задачи удаляется её история.** По ТЗ постановщик может удалять задачи, и история без задачи не имеет смысла. Напрямую удалить или изменить историю нельзя никому. Для реального проекта я бы предложил «мягкое удаление» (архив), чтобы история сохранялась навсегда.
10. Пользователя, у которого есть задачи или записи в истории, удалить нельзя (`on delete restrict`), чтобы не потерять следы в истории.

## Интерфейс
11. **Объект видят только те исполнители, у которых на нём есть задачи.** Внутри объекта исполнитель видит только свои задачи.
12. **«Мои задачи»** показываются только исполнителю. Задачи разделены на активные и принятые.
13. После входа постановщик попадает на «Объекты», а исполнитель на «Мои задачи».

## Что не успел или сознательно не делал
- Нет пагинации и поиска: для объёмов тестового задания они не нужны.
- Нет realtime-обновлений: изменения от других пользователей видны после перезагрузки страницы.
- Нет экрана управления пользователями: их создают в Supabase Dashboard, как сказано в ТЗ.
- Нет e2e-тестов интерфейса. Права проверяются автотестом на уровне базы (`npm run test:db`), а это главное.
- Ошибки из базы выводятся простым текстом, без отдельного оформления.
